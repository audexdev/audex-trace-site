Mid-track sample rate switch

Why the sample rate switches mid-track to the next track on Mac.

Apple Music prepares the next track before the current one ends. The prepared player writes its own format line to the macOS unified log while the current track is still playing. A switcher that treats the newest format line as what is playing now switches early.

Quick answer

Quick answer.

  • The symptom: Your output device's rate is right at the start of a track, then changes partway through the same track to the next track's rate. You hear a short interruption, and the rest of the track plays at the wrong rate.
  • The cause: Apple Music prepares the next track before the current one ends. The prepared player writes its own format line to the macOS unified log while the current track is still playing. A switcher that treats the newest format line as what is playing now switches early.
  • Scope: This behavior is not specific to one macOS version or one tool. It was reported against LosslessSwitcher in January 2025 and again in September 2026, and reproduced on a fork.
  • Audex Trace: Audex Trace attributes each format line to the player instance that wrote it and to the track Apple Music says is playing, so a line from a prepared next track is held back until the track actually changes.
What it looks like

What it looks like.

Consider a 44.1 kHz track followed by a 96 kHz track in your queue. At the start of the first track, your DAC shows 44.1 kHz. Somewhere during that track, sometimes in the middle and sometimes in the last few seconds, the DAC jumps to 96 kHz. The music drops out for a moment while the DAC re-locks, and the rest of the 44.1 kHz track is played with the output at 96 kHz, so macOS resamples it. When the 96 kHz track starts, nothing changes because the device is already at 96 kHz, so the switch looks correct again.

You see Audio MIDI Setup's sample rate for the output device, the DAC's own display, and the switcher's menu bar readout all move at the same moment.

The timing is unpredictable because it depends on when Apple Music decides to prepare the next item, which depends on buffering, track length, and queue changes.

Why it happens

Why it happens.

Apple Music on macOS plays each item in your queue through a player instance. Before the current item ends, it creates and prepares the next one so playback continues without a gap. The prepared instance decodes the beginning of the next track.

When an instance decodes, Music writes format lines (codec, bit depth, sample rate) to the unified log. The prepared instance writes its lines while the current instance is still playing.

A switcher that reads the log and applies the newest format line applies the next track's rate when the next track is prepared, not when it starts.

Anything that makes Music refresh its player state mid-track can trigger the same read: queue edits, Play Next, metadata or artwork updates. A contributor describing LosslessSwitcher's code in issue #231 on 2026-10-09 wrote that its track-change handler runs on every MediaRemote callback, including mid-track updates for the same track, and then applies the newest decoder log entry.

Reports

Where it has been reported.

  • vincentneo/LosslessSwitcher issue #159, opened 2025-01-09: switches to the next track's rate instead of the current track's. https://github.com/vincentneo/LosslessSwitcher/issues/159
  • vincentneo/LosslessSwitcher issue #231, opened 2026-09-29: macOS 27.0 (build 26A428), Music 1.7, LosslessSwitcher 2.0 and the horikei525 fork 4.4.2, iFi Go Bar. Correct switch at the start of the track, then a second switch partway through to the next track's rate; the reporter could not predict the timing. A contributor's comment on 2026-10-09 attributes it to Music preloading the next track and points to pull request #225 (opened 2026-09-20), which only runs detection on a real track change, resume, or seek and picks the log entry closest to that event. As of 2026-10-10 that pull request is open and not in a release. https://github.com/vincentneo/LosslessSwitcher/issues/231

These are two documented reports, not a measurement of how many people are affected.

Overlap features

What makes it worse.

Apple Music's overlap features, Song Transitions, AutoMix, and Crossfade, keep two player instances active around every track boundary on purpose. With them on, two instances can decode at once, and no log-based tool, Trace included, can promise an exact readout around the boundary.

Trace's Playback Verification screen states: "Turn off Song Transitions, AutoMix, or Crossfade. They can make detection delayed or unavailable around track changes."

The settings are in Music > Settings > Playback. AutoMix may be on by default on recent macOS versions, so check rather than assume it is off.

Audex Trace

What Audex Trace does.

Trace reads the same category of Music log lines but keeps track of which player instance wrote each line.

Trace keeps a current-track anchor from Apple Music's own now-playing state. While that anchor has not changed, a format line from a different player instance is treated as a possible preload of the next track and is not applied to the readout or to Auto Sample Rate Match. It becomes eligible only after Music reports that the track changed.

Lines from the same player instance do update the readout, so a format change within the same item is still reflected.

Upcoming tracks are shown separately in Playing Next, with their estimated format in Pro (queue quality estimates), so next is displayed as next rather than mixed into now.

In the developer's testing with Song Transitions, AutoMix, and Crossfade off, on macOS 15.4, 26.3, 26.3.1, 26.4.1, and 26.5, the readout and the automatic switch followed the playing track. With those features on, detection around track changes is best effort.

Trace is signed and notarized, needs no logging configuration profile, and requires a macOS administrator account because standard accounts cannot read the playback logs.

What Trace does not fix

What Trace does not fix.

The brief dropout when a DAC changes sample rate is the device re-locking to a new clock. Trace changes the device rate the same way other switchers do, so that gap exists with Trace too. This page is about switching at the wrong time, not about the gap.

With the overlap features on, Trace does not promise an exact readout at the boundary.

Trace does not take exclusive control of the output device and does not claim bit-perfect output.

Check it yourself

Check it on your own Mac.

You can run this check on your own Mac:

  1. In Music > Settings > Playback, turn off Song Transitions, AutoMix, and Crossfade.
  2. Queue a 44.1 kHz track followed by a 96 kHz track, or any two different rates.
  3. Open Audio MIDI Setup and watch the output device's sample rate during the first track.
  4. If the rate changes before the first track ends, you are seeing the preload switch.
  5. Download Audex Trace and run the free Playback Verification.It shows the detected track format, the current output format, and whether Trace can match them on this device. It changes nothing unless you press the apply button.

FAQ

Common questions.

No single version. Reports exist from January 2025 and September 2026; macOS 27 is the most recent. The mechanism, Music preparing the next item, has existed for years.

It removes the overlap at the boundary, but the next item is still prepared before the current one ends, so a newest-line switcher can still switch early. Turning the overlap features off is still recommended for any log-based tool.

It applies the switch when Music reports the track change and a format line for that track is attributed. The device re-lock gap at the switch still exists.

The playback logs are readable only by administrator accounts on macOS; standard accounts cannot run Playback Verification or live detection.
